# Reader benchmark (step 2 engine vs Python `flattrace stats`)

Method: one measured wall-clock run each of `python3 -m flattrace stats --json`
and `flattrace-read stats --json` over the same explicit file list, timed with
`time.perf_counter` around the subprocess. No repeats, thresholds or gates;
single runs reported as-is. Both commands read the same files and emit the
same report shape (asserted by `crates/flattrace-read/tests/cli_stats.rs`).

## Corpora

- Synthetic: generated by `bench/reader_bench.py` (deterministic seed 7,
  nested spans, errors with `count`, points, one `.jsonl.gz` member) under
  `build/reader/bench-work/synthetic/` (outside the repo).
- Real: the Zamil session traces (read-only; see the conformance corpus
  `real/` notes for the redaction route).

## Results (2026-10-26 UTC, build host: 16 CPUs, ~94 GB RAM shared with other work)

Single measured runs each. Both readers from this checkout; the Rust binary
is the release profile. Rust 1.94.1, Python 3.12.3, rusqlite 0.41.0 (bundled
SQLite), serde_json 1.0.150. Exit codes matched in every pair (0 clean,
1 unfinished evidence). The engine's max RSS on the real corpus was 26 MB.

| corpus | files | bytes | events | python stats | `flattrace-read stats` | ratio python/rust |
|---|---|---|---|---|---|---|
| synthetic (seed 7) | 40 | 11,199,064 | 39,842 | 1.92 s / 3.16 s | 1.24 s / 1.75 s | 1.55 / 1.81 |
| zamil-flattrace (read-only, live dir: 422 files round 1, 428 round 2) | 422–428 | ~65,000,000 | 183,519 | 8.35 s / 10.52 s | 15.14 s / 17.57 s | 0.55 / 0.60 |

The engine is faster on the small corpus and slower on the large real one
(~0.6x). The gap is roughly constant per unit of work, not a scaling
cliff: both readers stream with disk-backed quantiles, but the engine
retains full span records (payloads, points, children) for the digest/spans/
tree/compare/overlap queries while `flattrace stats` retains only duration
samples. Per-round load on this shared host moves single-run numbers
noticeably (see the two rounds above); treat them as approximate
observations, not tuned claims. Reducing the retained-detail cost is an
open optimization question, not a step-2 change.

Date (UTC): 2026-10-26. The host runs other work concurrently (a large
unrelated job was active during measurement); treat ratios as approximate
single observations, not tuned claims.

## Notes

- Timings are whole-CLI wall time (startup, file I/O, pairing, SQLite spill,
  JSON serialization), not steady-loop writer overhead; see `bench/README.md`
  for the writer harness, which this does not replace.
- The Python reader keeps completed samples in a disposable SQLite file and
  sorts there; the engine spills span records and samples to its own
  temporary SQLite file the same way. Memory stays proportional to open
  spans and small counters in both.
- `dominant_spans` tie order differs by construction: Python inherits
  hash-set order (varies with `PYTHONHASHSEED`), the engine uses
  alphabetical ties. The parity test normalizes ties before comparing.
