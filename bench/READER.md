# Reader benchmark (step 2 engine vs Python `flattrace stats`)

Method: three measured wall-clock runs each of `python3 -m flattrace stats --json`
and `flattrace-read stats --json` over the same explicit file list, timed with
`time.perf_counter` around each subprocess; the median is reported. No warmup,
thresholds or gates. Both commands read the same files and emit the
same report shape (asserted by `crates/flattrace-read/tests/cli_stats.rs`).

## Corpora

- Synthetic: generated by `bench/reader_bench.py` (deterministic seed 7,
  nested spans, errors with `count`, points, one `.jsonl.gz` member) under
  `build/reader/bench-work/synthetic/` (outside the repo).
- Real: the frozen agent-session snapshot `build/reader/bench-work/agent-snap/`
  (456 files, copied once; the live directory keeps growing and is never
  used for benchmarks). See the conformance corpus `real/` notes for the
  redaction route.

## Results (2026-10-26 UTC, build host: 16 CPUs, ~94 GB RAM shared with other work)

Three measured runs each, median reported (method: one `time.perf_counter`
span per `python3 -m flattrace stats --json` vs release
`flattrace-read stats --json` over identical explicit file lists; single
process per round, no warmup). Both readers from this checkout; the Rust
binary is the release profile. Rust 1.94.1, Python 3.12.3, rusqlite 0.41.0
(bundled SQLite), serde_json 1.0.150. Exit codes matched every pair (0 clean,
1 unfinished evidence). The engine keeps full span records in memory as
typed structs and spills only quantile samples (like stats.py).

| corpus (frozen) | files | bytes | events | python stats (3 runs → median) | `flattrace-read stats` (3 runs → median) | median ratio python/rust |
|---|---|---|---|---|---|---|
| synthetic (seed 7) | 40 | 11,199,064 | 39,842 | 1.55 1.41 1.28 → **1.41** | 0.62 0.59 0.72 → **0.62** | **2.27** |
| agent-snap | 456 | 94,182,395 | 251,092 | 10.66 10.65 8.99 → **10.65** | 3.64 5.16 5.21 → **5.16** | **2.06** |

The engine is faster on both corpora on the in-memory typed model: the
per-JSON-line parse happens once into typed structs with no re-serialization,
and only quantile samples touch SQLite. Earlier single-run numbers on the
noisy shared host differed run to run; the three-round medians above are the
record. The live trace directory is never benchmarked (it grows).

Date (UTC): 2026-10-26. The host runs other work concurrently (a large
unrelated job was active during measurement); treat ratios as approximate
single observations, not tuned claims.

## Notes

- Timings are whole-CLI wall time (startup, file I/O, pairing, SQLite spill,
  JSON serialization), not steady-loop writer overhead; see `bench/README.md`
  for the writer harness, which this does not replace.
- Both readers spill quantile samples to disposable SQLite files and sort
  there. The engine retains all span records, payloads and attached points
  in typed in-memory structures; SQLite does not bound that memory. Memory
  therefore grows with the retained corpus, not just open spans or counters.
- `dominant_spans` tie order differs by construction: Python inherits
  hash-set order (varies with `PYTHONHASHSEED`), the engine uses
  alphabetical ties. The parity test normalizes ties before comparing.
